Issue 1: Duplicate plugin registration

rule_15 | ❌ VIOLATION | DeviceSettings.cpp:37, 40

What's wrong: SERVICE_REGISTRATION(DeviceSettings, ...) and static Metadata both register the same class in the same source file. The OOP implementation is registered separately in DeviceSettingsImplementation.cpp, but that does not make the duplicate main-class registration valid.

Code found:

[DeviceSettings.cpp:37] SERVICE_REGISTRATION(DeviceSettings, API_VERSION_MAJOR, API_VERSION_MINOR, API_VERSION_PATCH);`n[DeviceSettings.cpp:40] static Metadata metadata(...)

Fix: Keep exactly one registration mechanism for DeviceSettings. Retain the distinct SERVICE_REGISTRATION(DeviceSettingsImp, ...) for the OOP implementation.

Issue 2: Constructor performs system initialization

rule_24 | ❌ VIOLATION | DeviceSettings.cpp:75-82

What's wrong: The constructor probes debug configuration paths with access() and calls rdk_logger_init(). This is resource/system initialization in the plugin constructor rather than Initialize().

Code found:

[DeviceSettings.cpp:75] if (access(DSMGR_DEBUG_OVERRIDE_PATH, F_OK) != -1) { ... }`n[DeviceSettings.cpp:82] if (rdk_logger_init(PdebugConfigFile) == 0) { ... }

Fix: Move logger and filesystem initialization to Initialize(), with cleanup in Deinitialize().

Issue 3: Manual Deinitialize from Initialize failure path

rule_27 | ❌ VIOLATION | DeviceSettings.cpp:323

What's wrong: Initialize() calls Deinitialize(service) after a Configure() failure. This couples partial-initialization rollback to the public lifecycle teardown path and can cause duplicate or invalid cleanup.

Code found:

[DeviceSettings.cpp:323] Deinitialize(service);

Fix: Use a dedicated rollback path that releases only resources acquired so far, or return the error and let the framework invoke Deinitialize() according to its lifecycle contract.

Issue 5: Cross-thread state is not synchronized

rule_47 | ❌ VIOLATION | DSController.cpp:83, 385, 1070, 1089

What's wrong: The resolution thread reads _dsMgr_thread_exit_flag and _hdcpAuthenticated, while callback paths write these shared variables without a common lock or atomic synchronization. volatile does not make concurrent access safe.

Code found:

[DSController.cpp:83] volatile bool DSController::_dsMgr_thread_exit_flag = false;`n[DSController.cpp:385] while (!_dsMgr_thread_exit_flag) { ... }`n[DSController.cpp:1070] _hdcpAuthenticated = true;`n[DSController.cpp:1089] _hdcpAuthenticated = false;

Fix: Use atomics for independent flags or protect every read and write with the same mutex; ensure condition-variable predicates use the corresponding lock.

Issue 6: Detached tasks outlive plugin-owned state

Code found:

[DSProductTraitsHandler.cpp:84] std::thread retryThread([controller, retryCount]() { ... });`n[DSProductTraitsHandler.cpp:88] retryThread.detach();`n[DSProductTraitsHandler.cpp:206] std::thread retry_thread(&UXController::SetBootloaderPatternAsync, this, pattern);`n[DSProductTraitsHandler.cpp:207] retry_thread.detach();

Fix: Schedule work through Core::WorkerPool with cancellation/lifetime ownership, or maintain joinable workers and stop/join them before destroying UXController.

Issue 7: COM notification HRESULTs are discarded

rule_63 | ❌ VIOLATION | DeviceSettings.cpp:194, 200, 206, 212, 218, 343-363

What's wrong: Component Register() and Unregister() calls discard their HRESULTs. Initialization can report success with notifications unregistered, and teardown cannot detect failed cleanup. DSPwrEventListener also ignores the PowerManager Register() result.

Code found:

[DeviceSettings.cpp:194] _mDeviceSettingsHDMIIn->Register(...);`n[DeviceSettings.cpp:218] _mDeviceSettingsDisplay->Register(...);`n[DeviceSettings.cpp:343] _mDeviceSettingsHDMIIn->Unregister(...);`n[DSPwrEventListener.cpp:350] _powerManagerPlugin->Register(...);

Fix: Capture each HRESULT, test it, and propagate/log failures with a defined rollback policy. Set registration state only after a successful Register().
