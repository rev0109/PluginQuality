Issue 1

rule_04 - VARIABLE_IS_NOT_USED Accuracy
Status: ❌ VIOLATION | Evidence: [PlayerInfo.cpp:142,168]

What's wrong: The Deinitialize parameter service is annotated unused but referenced by ASSERT(service == _service). The local result from _player->Release() is also annotated unused and then checked by ASSERT(result == Core::ERROR_DESTRUCTION_SUCCEEDED).

// [PlayerInfo.cpp:142-144,168-169]
void PlayerInfo::Deinitialize(PluginHost::IShell* service VARIABLE_IS_NOT_USED)
{
    ASSERT(service == _service);
    VARIABLE_IS_NOT_USED uint32_t result = _player->Release();
    ASSERT(result == Core::ERROR_DESTRUCTION_SUCCEEDED);
}

Fix:

void PlayerInfo::Deinitialize(PluginHost::IShell* service)
{
    ASSERT(service == _service);
    const uint32_t result = _player->Release();
    ASSERT(result == Core::ERROR_DESTRUCTION_SUCCEEDED);
}

Issue 2

rule_27 - No Manual Deinitialize() in Initialize
Status: ❌ VIOLATION | Evidence: [PlayerInfo.cpp:137,146,180]

What's wrong: On an initialization failure, Initialize() calls Deinitialize(service) and then returns a non-empty error. Thunder calls Deinitialize() for a failed initialization as well. The second call reaches _service->Unregister() and later releases a shell pointer that the first call already nulled, so the failure path can crash.

// [PlayerInfo.cpp:136-138,146,180]
if (message.length() != 0) {
    Deinitialize(service);
}
return message;

_service->Unregister(&_notification);
_service->Release();
_service = nullptr;

Fix:

// Initialize: return the error and let Thunder perform teardown.
if (!message.empty()) return message;

// Deinitialize: guard every partially acquired resource before cleanup.

Issue 5

rule_41 - Reverse-Order Cleanup
Status: ❌ VIOLATION | Evidence: [PlayerInfo.cpp:150-168]

What's wrong: Initialization registers PlayerProperties before Dolby, but teardown unregisters PlayerProperties first. It also releases the audio iterator before the later-acquired video iterator. After the required first service Unregister, the remaining resources should be unwound in reverse acquisition order.

// [PlayerInfo.cpp:150-168]
Exchange::JPlayerProperties::Unregister(*this);
_audioCodecs->Release();
_videoCodecs->Release();
Exchange::Dolby::JOutput::Unregister(*this);
_dolbyNotification.Deinitialize();
_dolbyOut->Release();

Fix:

// Unregister Dolby first, then PlayerProperties; release video before audio.
Exchange::Dolby::JOutput::Unregister(*this);
_dolbyNotification.Deinitialize();
Exchange::JPlayerProperties::Unregister(*this);
_videoCodecs->Release();
_audioCodecs->Release();

Issue 6

rule_43 - AddRef/Release Balance
Status: ❌ VIOLATION | Evidence: [PlayerInfo.cpp:137,180]

What's wrong: The explicit cleanup on Initialize failure releases the stored IShell reference, but the non-empty error return causes framework cleanup to run again. The second release is not balanced by an AddRef and occurs through a pointer already set to null.

Fix: Remove the direct call to Deinitialize from Initialize and make Deinitialize safely handle partial acquisition once.

Issue 7

rule_47 - Shared State Protected by CriticalSection
Status: ❌ VIOLATION | Evidence: [PlayerInfo.cpp:184,336-338]

What's wrong: Deactivated() runs on the remote-connection callback thread and reads _connectionId and _service, while Deinitialize clears those members and releases the service on the lifecycle thread. No lock or atomic/lifetime protocol protects those accesses.

// [PlayerInfo.cpp:184,336-338]
_connectionId = 0;
if (_connectionId == connection->Id()) {
    ASSERT(_service != nullptr);
    Core::IWorkerPool::Instance().Submit(
        PluginHost::IShell::Job::Create(_service, ...));
}

Fix: Coordinate callback state and shell lifetime with a lock or equivalent synchronization, and make teardown wait for or invalidate callbacks before releasing the pointer.

Issue 8

rule_56 - COM Reference Counting Correctness
Status: ❌ VIOLATION | Evidence: [PlayerInfo.cpp:137,180]

What's wrong: The same failure path breaks COM reference-counting correctness: _service receives one AddRef in Initialize, but direct Deinitialize plus framework-driven Deinitialize can attempt two releases.

Fix: Let Thunder own failure teardown and guard each cleanup action so every acquired reference is released exactly once.

Issue 9

rule_58 - JSON-RPC Handlers Are Re-entrant Safe
Status: ❌ VIOLATION | Evidence: [PlayerInfo.cpp:229-242]

What's wrong: Process() and JSON-RPC handlers can call Info() concurrently. Each call resets and advances the same member codec iterators, so one request can disturb another request's iteration.

// [PlayerInfo.cpp:231-242]
_audioCodecs->Reset(0);
while (_audioCodecs->Next(audio)) { ... }
_videoCodecs->Reset(0);
while (_videoCodecs->Next(video)) { ... }

Fix: Obtain per-request iterators or serialize the complete iterator reset/read sequence with a lock shared by every caller.

rule_62 - Deinitialize Pointer Safety
Status: ❌ VIOLATION | Evidence: [PlayerInfo.cpp:146,180,336-338]
